= Unoserver Container Image

Container image for unoserver

== Fork-specific scope

CI publication blocks fixable HIGH/CRITICAL findings and permits findings without a listed fix with explicit warning annotations. See link:docs/ci-security-policy.md[the CI security policy]. Both legacy manual workflow entrypoints delegate to the custom gated workflows.

This repository is a fork of `unoconv/unoserver-docker`. Some content below is inherited from upstream and may not fully reflect fork-specific behavior.

In this fork branch `custom`, `Dockerfile` is intentionally kept aligned with upstream to reduce merge friction. Use `Dockerfile.custom` for branch-specific hardened builds.

Published images carry their release in the `org.opencontainers.image.version` label, the same
`A.B.C-custom.N` as their version tag, and the commit they were built from in
`org.opencontainers.image.revision`. Images published before these labels were added carry
neither: their release is only the tag that points at their digest.

The fork is designed and validated primarily for `linux/amd64`.

`linux/arm64` support is kept for upstream compatibility and multi-arch publishing continuity.

Workflow verification steps are architecture-aware:

* Build and image scanning run for both `linux/amd64` and `linux/arm64`
* Integration validation with `pytest` runs only on `linux/amd64`

Image rebuild triggers:

* Every push to `custom` starts `rebuild-on-push.yml`, which runs the daily
  `scan-active-image.yml` workflow with the same gates: build, Trivy, integration test,
  publication, final scan of `latest`.
* The daily run rebuilds when the active `latest` image was built from another commit of this
  repository (its `org.opencontainers.image.revision` label differs from the `custom` head,
  or is missing), when `latest` does not exist yet, or when the active image has HIGH or
  CRITICAL findings. A commit-driven rebuild happens whether or not the upstream version
  changed: the version stays `A.B.C` and only `N` in `A.B.C-custom.N` increases.
  Documentation-only commits are included.
* Daily, manual and push-triggered runs of `scan-active-image.yml` are serialized, so two of
  them never both rebuild the same commit: a run started while another is in progress waits,
  and GitHub keeps only the most recent waiting run. A waiting manual `force_rebuild`
  replaced this way must be requested again. A `publish-custom.yml` run started directly is
  serialized only with other publications.
* To rebuild without a new commit, request one manually:
  `gh workflow run scan-active-image.yml --repo carvvf/unoserver-docker -f force_rebuild=true`

A successful rebuild and clean final scan complete the workflow successfully. Review
workflow summaries and published tags, then pull the new image and redeploy downstream
services. Real build, scan, or integration-test failures still fail the workflow.

Tag retention: `retention-cleanup.yml` runs weekly and deletes GHCR versions older than 60
days. It keeps:

* the version tagged `latest`
* the ten newest `-custom.N` rebuilds, whatever their age, for rollback
* every version updated in the last 60 days
* the platform and attestation manifests of every kept tag. Each tag names an OCI index, and
  GHCR lists its `linux/amd64`, `linux/arm64` and attestation manifests as separate untagged
  versions; deleting them would make the kept tag unpullable.

The workflow reads every page of the listings and fails without deleting anything if it
cannot read a kept tag's index. Review its decisions with
`gh workflow run retention-cleanup.yml --repo carvvf/unoserver-docker -f dry_run=true`.
Completed workflow runs older than 60 days are deleted by the same workflow.

Dependency update pull requests: `renovate.yml` runs Renovate weekly (Monday night,
Europe/Rome) and on demand. It opens or refreshes one cumulative pull request with the
updates the image workflows do not take on their own:

* a new Java major or Alpine release of the `eclipse-temurin` base image tag
* a new unoserver major (`UNOSERVER_MAJOR`)
* a new Trivy release line (`TRIVY_LINE` in `scripts/trivy/trivy_image.sh`)
* new versions of the GitHub Actions and of the Renovate release the workflow runs, and of
  `docker-bench-security`

A new upstream release or main commit gets a pull request of its own, described below.
Nothing is merged automatically. Merging the pull request pushes to `custom`, which rebuilds
and publishes through the usual gates. Renovate runs as a GitHub App installed on this
repository: its client ID is the repository variable `RENOVATE_APP_CLIENT_ID` and its private
key the secret `RENOVATE_APP_PRIVATE_KEY`. Issues stay disabled, so there is no Dependency
Dashboard. Run it on demand with
`gh workflow run renovate.yml --repo carvvf/unoserver-docker`.

Upstream baseline: `publish-custom.yml` pins the upstream release and main commit merged into
`custom` (`UPSTREAM_RELEASE` and `UPSTREAM_MAIN`, as `TAG@COMMIT`). The release sets the
`A.B.C` of `A.B.C-custom.N`. Publication reads only these values and never fetches upstream,
so new upstream commits or releases do not block rebuilds, security rebuilds included. Its
preflight fails when a pinned commit is not in the history of the built commit. When upstream
moves, Renovate opens an "upstream baseline" pull request that updates both values; merge
upstream into that pull request's branch up to the proposed main commit, review it against
the fork-specific files, then merge it.

== How to use it

NOTE: The `docker` can normally be replaced with `podman` as well.

=== In interactive mode

Just run:

[source,bash]
----
docker run -it -v <your directory>:/data/ ghcr.io/unoconv/unoserver-docker
----

After you start the container, you can use link:https://github.com/unoconv/unoserver#unoconvert[unoconvert] command to convert documents using LibreOffice.

or to convert directly using unoconvert:

[source,bash]
----
docker run -it -v <your directory>:/data/ ghcr.io/unoconv/unoserver-docker unoconvert /data/document.docx /data/document.pdf
----

Docker maps your directory with /data directory in the container.

You might need to add the option `:z` or `:Z` like `<your directory>:/data/:z` or `<your directory>:/data/:Z` if you are using SELinux. See link:https://docs.docker.com/storage/bind-mounts/#configure-the-selinux-label[Docker docs] or link:https://docs.podman.io/en/latest/markdown/podman-run.1.html#volume-v-source-volume-host-dir-container-dir-options[Podman docs].


=== In non-interactive (remote) mode

[source,bash]
----
docker run -p 2003:2003 ghcr.io/unoconv/unoserver-docker
----

After you start the container, you can use link:https://github.com/unoconv/unoserver#unoconvert[unoconvert] command to convert documents using LibreOffice.

NOTE: You must use `--host-location` otherwise unoconvert will default to local although running unoserver in a container should be handled as remote.

[source,bash]
----
unoconvert --host-location remote example.docx example.pdf
----

=== Conversion timeout

In non-interactive mode, one conversion may take at most `UNOSERVER_CONVERSION_TIMEOUT` seconds
(a positive integer, default `60`). Past it the container exits with status 1, and the restart
policy of `docker-compose.latest.yml` brings up a clean service, so that a document that hangs
LibreOffice cannot block the conversions after it. The client receives an error, and other
conversions fail until the service is back, a few seconds later.

Keep it above the timeout of the client: a conversion that the client has given up on is the only
one that should be stopped. A container run without a restart policy stays down.

=== Network

`docker-compose.latest.yml` puts the service on `unoserver-docker-net`, an `internal` network with no
way out, and publishes no port. LibreOffice fetches images that a document links to while converting
it, so a document could otherwise make this host send requests to its own network or to the
internet. Clients reach the service by name on that network. A client that also needs outbound access
joins a second network of its own.

To reach the service from the host during development, use `scripts/unoserver/run-local.sh`, which runs
it apart from this network with the port published on loopback.

=== Optional AppArmor confinement

This fork includes an optional AppArmor profile for Ubuntu 24.04 hosts and
compatible AppArmor-enabled Linux systems.

The profile is intended for the stateless network service runtime. It does not
support the inherited interactive examples that bind mount host directories to
`/data`; `/data` is intentionally denied by the profile.

[source,bash]
----
scripts/apparmor/unoserver-profile.sh check
sudo scripts/apparmor/unoserver-profile.sh enable
APPARMOR_PROFILE=docker-unoserver scripts/unoserver/run-local.sh
----

For Docker Compose, enable the profile and add the override file:

[source,bash]
----
sudo scripts/apparmor/unoserver-profile.sh enable
docker compose -f docker-compose.latest.yml -f docker-compose.apparmor.yml up
----

See link:docs/apparmor.md[docs/apparmor.md] for the threat model,
operational impact, disable/remove commands, and troubleshooting.
== FAQ

Q. Why do I get an error during when converting is writing/exporting to file?

A. It's very likely that you haven't given the container write permission to the mounted data directory. See: link:https://github.com/unoconv/unoserver-docker/issues/44[Issue #44]
